# Commit Assistance Methodology

Use this skill to ensure every repository change is documented with a structured, machine-readable, and human-scannable commit message.

## Phase 1: Intent Classification

Analyze the staged changes to determine the primary intent. Choose the most appropriate type:

- **feat**: A new feature or capability for the user.
- **fix**: A bug fix or resolution of an error.
- **docs**: Documentation only changes (README, wiki, comments).
- **style**: Changes that do not affect the meaning of the code (formatting, missing semi-colons, white-space).
- **refactor**: A code change that neither fixes a bug nor adds a feature (improving logic, simplifying code).
- **perf**: A code change that improves performance.
- **test**: Adding missing tests or correcting existing tests.
- **build**: Changes that affect the build system or external dependencies (example scopes: gulp, webpack, npm).
- **ci**: Changes to CI configuration files and scripts (example scopes: Travis, Circle, GitHub Actions).
- **chore**: Other changes that don't modify src or test files.

## Phase 2: Structural Construction

Construct the message using the following standard format:
`<type>([optional scope])[optional !]: <description>`

### Implementation Rules

1. **Scope**: Use a noun describing a section of the codebase surrounded by parenthesis (e.g., `feat(parser):`).
2. **Breaking Changes**: Indicate a breaking change by adding an exclamation mark before the colon (e.g., `feat(api)!: change response format`) and adding `BREAKING CHANGE: <description>` in the footer.
3. **Description**:
    - Use the imperative, present tense: "change" not "changed" or "changes".
    - Don't capitalize the first letter.
    - No dot (.) at the end.

## Phase 3: Detailed Context (The Body)

If the change requires more explanation than the 50-character subject line allows:

1. Use a blank line between the subject and the body.
2. Explain the *what* and *why* of the change (the code itself explains the *how*).
3. Use bullet points for multiple related changes.

## Phase 4: Metadata (The Footer)

Use the footer to link to issue trackers or provide technical metadata:

- `Closes #123` (preferred for issue references — use `Closes`, not `Fixes`)
- `See-also: link-to-spec`
- `BREAKING CHANGE: The old login endpoint has been removed.`

At the end include:
- `🤖 Generated with <model> <model version>` where LLM name/version is similar to `Claude Opus 4.6`

Do NOT include `Co-Authored-By` trailers — this is forbidden by CLAUDE.md.
Do not include any other statements about being generated by an LLM.

## Branch Integration

Prefer **merge over rebase** when bringing a branch up to date with main. Since this project uses squash merges, rebasing rewrites history unnecessarily and requires a force-push, with no benefit.

## Phase 5: Quality Checklist

- [ ] Is the type lowercase and descriptive?
- [ ] Is the subject line roughly 50 characters or less?
- [ ] Is there a blank line before the body?
- [ ] Are lines in the body wrapped at 72 characters?
- [ ] Did I use the imperative mood?
- [ ] If this is a new feature (`feat`), did I add relevant tips to tips.json?
